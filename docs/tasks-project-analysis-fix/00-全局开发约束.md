## 1. 证据纪律（本系列特有）

- 任务文档内的 file:line 证据来自 **2026-09-13 核查快照**。修复前必须以
  **函数名/结构名为锚**重新定位（行号可能已漂移）；若证据已不成立（已被
  其他提交修复），在时间线注明、任务置 ⏸️，**禁止强行修改**。
- 修复中如发现报告结论有误，同步修正分析报告 §3/§5 对应条目，不允许
  「代码改了但报告仍是旧结论」。
- 新增结论（修复中发现的新问题）同样要求 file:line 实证，不接受臆测。

## 2. 状态三处同步

- 任务状态流转时同时更新：本系列 `README.md` 总表 + 任务文档「进度」章节
  + 分析报告 §3 对应条目（完成时行尾追加「✅ 已修复（PAF-XX，日期）」）。
- 状态只允许 ⬜ → 🟦 → ✅（或 ⏸️）；时间线每步追加一行（日期 + 结果 +
  验证命令）。

## 3. 最小修复与簇协同

- 只修任务文档「问题描述/修复建议」范围内的问题，不顺手重构无关代码；
  牵出的独立问题新开 PAF-XX（接续编号），不在原任务里扩张。
- **簇内同批实施**（改一处必须回归全簇）：
  - 启动链路簇：PAF-02 / PAF-03 / PAF-06 / PAF-07（+PAF-09），共用
    spawn/stop/restart 状态机与 launch_cache；
  - 流式底座簇：PAF-08 + PAF-25，共用 `run_git_streaming`，取消语义与
    实时输出一起接；
  - 内存三连 PAF-12、watcher 四缺陷 PAF-13、终端失效三连 PAF-14 各自为簇。

## 4. 平台与兼容性

- 涉及路径/进程/可执行文件检测的修改，先对照 AGENTS.md「平台兼容性开发
  规范」（路径归一化、PATHEXT、`CREATE_NO_WINDOW`、进程组、GBK 等）。
- Windows 跑测试必须 `GW_TEST_MANIFEST=1 cargo test --lib`；环境相关测试
  （mvn/JDK/node/网络）探测不到就 skip 并打印原因，不硬失败。
- 断言含路径的输出先 `replace('\\', "/")` 归一化。

## 5. 改动前的影响分析

- 修改任何函数/类/方法前，按 AGENTS.md 要求跑 GitNexus `impact` 分析并向
  用户报告影响面；HIGH/CRITICAL 风险先警告再动手。
- 提交前跑 `detect_changes()` 核对改动范围只涉及预期符号。

## 6. 验证基线

- Rust 后端改动：`cargo test --lib`（Windows 加 `GW_TEST_MANIFEST=1`）。
- 前端改动：`pnpm build`（含 vue-tsc 类型门禁）。
- 触及 IPC 契约（命令/事件/payload）：同步更新 golden fixture 并跑
  `ipc_golden` 相关测试。
- 能写失败测试的先写失败测试；修复 P0 项必须带回归测试。
