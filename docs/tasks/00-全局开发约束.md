# 00 全局开发约束（横切关注点）

> 适用：**T-01 ~ T-32 全部任务**。
> 本文件记录「开发任何单个功能都必须遵守」的全局注意点，与各任务文档里的「架构/性能注意点」**叠加生效**：
> - 任务文档只写该任务**特有**的注意点；
> - 这里写贯穿全文的**全局**约束。
>
> 开发任何单个功能前，先读本文件。
> 括注的 `§` 号指 `docs/GitWorkspace 产品需求与技术架构 Roadmap.md` 的章节号。

---

## 1. 四条总原则（§77）

- **Multi-Repo First**：每个新功能先问一句「能不能同时作用于多个 Repository」。
- **Performance First**：禁止全量扫描、重复计算、无意义 IPC、无限并发、阻塞 UI；优先 Cache / Incremental / Parallel / Lazy / Batch。
- **Safety First**：危险操作必须明确影响范围、数据风险、用户确认、可恢复。
- **AI as Assistant**：AI 只建议 / 解释 / 分析 / 生成，**不默认自动修改 / 自动提交 / 自动 Push**。

## 2. 性能横切（§G4、§45、§65）

- 所有性能指标以 **T-07 Benchmark 实测为准**，不凭感觉；改动性能关键路径后要跑 Benchmark 对比。
- 缓存分层固定为 **Memory（LRU，热数据）→ SQLite（持久元数据）→ Git 仓库（冷数据按需打开）**，LRU 必须有上限。
- 并发按任务类型限流（§45 建议 Status 16 / Fetch 8 / Pull 4 / Push 4 / Index 4），**禁止按仓库数无上限 fork git 进程**。
- IPC 大 payload 必须分页 / 流式；高频事件批量聚合推送，不阻塞 UI。
- 默认压力假设是 **1000 仓库**：空闲内存 < 500MB，UI 全程保持响应。

## 3. Git 引擎边界（§36、§46）

- **libgit2 `Repository` 非 `Send/Sync`**：不跨线程复用句柄；并行任务各自独立 `open`/`drop`；缓存里只放纯数据（oid / status / 数值），**不放 libgit2 句柄**。
- **ahead/behind 只用本地 remote-tracking ref 计算**；任何「刷新列表 / 打开 Dashboard」都**不得触发网络 fetch**。
- 本地操作走 libgit2（status / diff / commit / add / restore / history / branch / tag）；网络操作走系统 git CLI（fetch / pull / push / credential / SSH / LFS）。

## 4. 操作安全（§46、§47）

- 危险操作分级 **Safe / Warning / Dangerous**；Dangerous 必须二次确认并明确列出「仓库 / 分支 / 文件 / 潜在数据丢失」。
- **Force Push 默认禁用**，用户显式开启；推荐 `--force-with-lease` 作为默认方案。
- Reset / Rebase / 删除类操作前，提示可用 reflog / stash 保底，保证**可恢复**。

## 5. Secret 与数据安全（§69、§70、§71、§72）

- **API Key 不落盘**（保持现状）；后续升级 OS Credential Store。
- **AI 请求前 + Commit 前**都做 Secret 检测（AWS Key / GitHub Token / JWT / Private Key / Password / DB URL）。
- AI 发送前必须 **Preview + 可 Exclude 文件/目录**，处理策略 Warning / Mask / Exclude。
- Commit 安全检查：Secret Scan + Large File Scan + Forbidden File Scan（`.env`、`*.pem`、`*.key`、`credentials.json`）。
- **日志中 Secret 必须脱敏**。

## 6. 数据层（§41、§42、§67）

- SQLite：`WAL` + `foreign_keys` + `busy_timeout` + `synchronous=NORMAL`。
- **单写者模型**：写侧串行化（单写连接 + 队列，或短事务 + 重试），多 worker 并发写不冲突。
- 批量写入用事务 + Prepared Statement，**禁止逐文件逐条 INSERT**。
- schema 变更走**版本化迁移**，不做破坏性变更；异常退出后可恢复，无库损坏 / 死锁 / 残留锁。

## 7. 错误与日志（§44、§63）

- 统一 `GitWorkspaceError`，分类 `RepositoryError / GitError / NetworkError / ConflictError / TaskError / IndexError / AIError / PermissionError / IOError`。
- 错误携带结构化字段：`code / message / repository / operation / details / recoverable`，能穿透 IPC 到 UI。
- 日志分级（Debug/Info/Warn/Error/Trace）并按模块分流（app / git / task / ai / performance），可导出 / 清空。

## 8. Offline First（§68）

- 核心 Git 功能**不依赖网络**：Status / Diff / Commit / Branch / Merge / Rebase / History / Stash / Reflog / Search。
- AI 与远程平台属于增强能力，缺失时不影响核心功能。

## 9. 文件监听与事件（§37、§39）

- watcher 按**每仓库粒度**分片监听，不搞「整个 workspace 一个全局 watcher」。
- 变更链路固定为：`文件变化 → 定位受影响仓库 → 增量 status → 事件聚合推送`，**禁止触发全量扫描**。
- 高频事件（如批量操作完成时）在发送端聚合 / 节流，不指望 UI 侧硬扛。

## 与任务文档的配合方式

- 每个任务文档的「验收标准」里，性能项统一标注「以 T-07 Benchmark 实测为准」。
- 任务文档的「架构/性能注意点」只写该任务特有的坑（如 T-17 的 worktree `.git` 文件形态）；本文件第 2、3 节的通用约束不再逐条重复。
- 若某任务与全局约束有冲突（例如临时放宽并发上限），必须在任务文档里显式说明原因与边界，否则默认遵守本文件。
